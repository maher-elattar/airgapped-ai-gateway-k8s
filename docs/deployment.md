# Deployment Guide

Deployment is where the design stops being a diagram. The goal is not to install
a controller and immediately point traffic at it. The goal is to make the gateway
observable, reversible, and boring before it ever sits in the request path.

![Discover, apply, verify, cutover, and rollback sequence](assets/diagrams/rendered/deployment-sequence.svg)

## Deployment model

The flow is staged:

1. Discover the current model and edge state.
2. Prepare and verify the offline dependency set.
3. Render the selected Kustomize overlay.
4. Produce a deterministic plan.
5. Review the plan before any mutation.
6. Save a pre-change snapshot.
7. Apply exactly what the approved plan lists.
8. Verify the internal gateway path.
9. Cut over the edge only after that path is proven.

The reason for the staging is failure isolation. A controller issue, a route
issue, a policy issue, an edge issue, and a backend issue should never all be
live suspects at the same moment.

## Source of truth

The source of truth lives in the repository:

- [examples/config](../examples/config) holds the example platform, model,
  consumer, and registry settings the tests run against.
- [manifests/baseline-v1.3.1](../manifests/baseline-v1.3.1) holds the Kustomize
  bases and overlays.
- [airgap/sources.lock.yaml](../airgap/sources.lock.yaml) pins the dependency and
  image set.
- [src/airgap_ai_gateway](../src/airgap_ai_gateway) holds the planner, executor,
  verifier, redaction, rollback, and bundle logic.

Runtime objects generated by the controller get inspected during verification.
They are not where platform changes belong.

## Choose the profile

| Profile | Use it when | Notes |
| --- | --- | --- |
| `kind-demo` | You need a static rendered demo overlay | Single replica and demo-only labels |
| `kind-e2e-lab` | You want the disposable behavioral proof | Uses mock OpenAI-compatible Services |
| `retained-nginx-edge` | An existing NGINX edge stays in the traffic path | Public cutover is separate from gateway install |
| `production-reference` | You need the production-oriented reference shape | HA and persistence assumptions are explicit |

The retained-edge profile is the conservative migration path: prove the gateway
internally first, change the edge later.

## Prepare the air-gap dependency set

Locally:

```bash
make airgap-demo
```

For a real environment, the same command family takes the intended compatibility
set and internal registry:

```bash
airgap-ai-gateway bundle build \
  --lock-file airgap/sources.lock.yaml \
  --compatibility-set baseline-v1.3.1 \
  --registry registry.example.internal:5000 \
  --dist-dir dist/airgap-bundles

airgap-ai-gateway bundle verify \
  --lock-file airgap/sources.lock.yaml \
  --compatibility-set baseline-v1.3.1 \
  --bundle-dir dist/airgap-bundles/baseline-v1.3.1
```

Then generate the exact registry promotion plan:

```bash
airgap-ai-gateway registry promote \
  --lock-file airgap/sources.lock.yaml \
  --compatibility-set baseline-v1.3.1 \
  --registry registry.example.internal:5000 \
  --output-file dist/airgap-bundles/promotion-plan.json
```

Every cluster node has to be able to reach the promoted registry.

## Plan before apply

Create a deployment plan:

```bash
airgap-ai-gateway --config examples/config deploy plan \
  --overlay retained-nginx-edge \
  --apply-mode server-side-dry-run \
  --output-dir runs/plans/deploy
```

Review both outputs:

- `plan.json` is the machine contract the executor follows.
- `plan.md` is the operator summary.

The plan captures the overlay, namespace, expected context, apply mode, actions,
resources, and notes. If it does not describe the change you meant to make, fix
the source. Do not apply it and adjust afterwards.

## Apply from the approved plan

Apply needs the same safety inputs every time:

- Exact expected Kubernetes context.
- Apply mode matching the reviewed plan.
- Confirmation token from configuration.
- Plan JSON.
- Pre-change snapshot JSON.
- Optional redacted command log path.

Capture the snapshot from the approved plan:

```bash
airgap-ai-gateway snapshot create \
  --plan-file runs/plans/deploy/plan.json \
  --expected-context kind-airgap-ai-gateway \
  --output-file runs/snapshots/pre-change.json
```

```bash
airgap-ai-gateway --config examples/config deploy apply \
  --expected-context kind-airgap-ai-gateway \
  --apply-mode server-side-dry-run \
  --confirm I_UNDERSTAND_DISPOSABLE_CONTEXT_ONLY \
  --plan-file runs/plans/deploy/plan.json \
  --snapshot-file runs/snapshots/pre-change.json \
  --commands-log runs/reports/deploy/commands.log
```

Move to a live-mode plan only after the same workflow has been reviewed for live
operation.

## Verify before cutover

Before any edge traffic changes, prove the internal path:

- Gateway `Programmed=True`.
- HTTPRoute `Accepted=True`.
- HTTPRoute `ResolvedRefs=True`.
- AgentgatewayPolicy `Accepted=True`.
- AgentgatewayPolicy `Attached=True`.
- Missing and unknown keys return 401.
- Denied consumers return 403.
- Allowed consumers return 200.
- Low-limit traffic reaches 429.

The runbook is [verification.md](verification.md).

## Cut over the retained edge

Plan cutover as its own operation:

```bash
airgap-ai-gateway --config examples/config cutover plan \
  --overlay retained-nginx-edge \
  --apply-mode server-side-dry-run \
  --output-dir runs/plans/cutover
```

Apply once the plan shows both the edge change and the rollback anchor:

```bash
airgap-ai-gateway --config examples/config cutover apply \
  --expected-context kind-airgap-ai-gateway \
  --apply-mode server-side-dry-run \
  --confirm I_UNDERSTAND_DISPOSABLE_CONTEXT_ONLY \
  --plan-file runs/plans/cutover/plan.json \
  --snapshot-file runs/snapshots/pre-cutover.json \
  --commands-log runs/reports/cutover/commands.log
```

If the internal gateway tests passed and the public tests fail, the search space
is now small: edge routing, DNS, TLS, firewalling, Host preservation, or the
public path.

## Greenfield exposure

A greenfield platform can expose the gateway directly, but treat that as its own
design decision. DNS, TLS, firewalling, load balancer type, and rollback behavior
all need to be settled before the gateway becomes public.

## What success looks like

A finished deployment leaves behind:

- Reviewed plan JSON and Markdown.
- Pre-change snapshot.
- Redacted command log.
- State ledger.
- Verification report.
- A clear rollback point.

If any of those are missing, the deployment is not done yet, whatever the Pods
say.
